# 永久地址身份归 TeslaMate，适配器仅保留缓存

## 目标与价值

用户选择第二种方案：由 TeslaMate/PostgreSQL 统一管理永久地址身份、原始 WGS84 坐标和必要的来源信息；适配器仅负责解析和可丢弃缓存。消除第二套必须与应用数据库配套恢复的永久坐标映射，降低长期备份与恢复成本。

追加交付：维护镜像版本与 GitHub Releases，让每次实际发布的双镜像更新可读、可追溯；自动跟进显示上游版本变化。

## 实施前背景与证据

- F1：当前 SQLite identities 永久保存坐标、编号、可信 OSM 来源及境外路由证据，cache 按身份/语言/策略保存响应。见 adapter/server.py:324、380、418、520。
- F2：TeslaMate 的 addresses 同时保存坐标。当前 find_address 先解析再插入；details 的 /lookup 只传编号。固定上游调用链和约束见 research/application-ownership.md。
- F3：地址坐标目前为 numeric(8,6)/numeric(9,6)，SQLite 原坐标不舍入。直接用旧 PG 坐标去重会错误合并更高精度的历史点。见 research/application-ownership.md 的坐标精度证据。
- F4：当前刷新替换 raw，但保留数据库主键、坐标和行程/充电关联；切换供应商后 raw 不一定包含先前可信来源。见 patches/0002-refresh-address-fields.patch:40、296；adapter/server.py:524。
- F5：旧正数身份不能当作本适配器的可信永久身份；默认官方 Nominatim 路径需要保持兼容。见 .trellis/spec/backend/contracts.md:24、30。
- F6：此前 README 删除已经在工作区中，仅涉及用户指定的说明；本任务不得恢复这些段落或混入无关功能。
- F7：当前版本/双镜像发布已有门禁但没有 GitHub Release writer；固定版本与浮动标签可能结果不同，完成判定尚未包括记录。见子任务 research/release-records.md（scripts/image_context.py:48-90、scripts/publish_images.sh:96-193、.github/workflows/ci.yml:162-225）。

## 需求

- R1：永久坐标仅以应用 addresses 为权威；稳定负身份的生成、精确坐标去重和来源元数据由 TeslaMate/PostgreSQL 管理。
- R2：保留历史数据库主键、负 osm_id、原始 WGS84 坐标、行程与充电关联。新身份不得与旧库已分配范围冲突。
- R3：应用请求携带身份、原坐标及经验证的来源上下文；适配器不访问 PostgreSQL、不需要应用数据库凭据。
- R4：适配器只持有可重新生成的结果缓存及非永久的限流状态；缓存丢失、清理、TTL 到期、重启或供应商/语言切换不影响地址身份和刷新能力。提供仅针对缓存的过期清理机制。
- R5：保留高德/百度/OSM 路由、临时 GCJ-02 查询转换、默认语言、可信 OSM 批量刷新、限流、批次上限、deadline 和固定错误语义；新协议的应用与适配器日志均不泄露请求体、坐标、地点或密钥。
- R6：并发首次请求同一坐标收敛到同一地址；新适配器路径失败不生成 Unknown 或空白占位。单个地址持久化与一次迁移提交保持原子性，lookup 不返回部分成功列表；保留上游行程起终点独立解析、逐地址和跨批刷新行为，默认 Nominatim 的 Unknown 语义不改。
- R7：历史迁移提供先审计、后显式导入的可复核流程。在恢复副本中验证精度、来源、全分配 ID 范围和回滚条件。缺少可靠证据或存在冲突时停止，不猜测或自动改号。
- R8：默认官方 Nominatim 路径和历史正身份保持原有行为；文档、Compose 示例、应用/适配器契约测试及镜像启动检查同步更新。
- R9：每次实际完成核验的 georelay/georelay-adapter 固定发布有对应 exact-source Release，包含本项目可读更新、两镜像版本/digest、真实发布结果。沿用现有版本方案；自动上游跟进明确旧版本 → 新版本和官方来源；beta 与正式版准确区分，幂等补录不重建固定内容。
- R10：可信 Release 记录、失败恢复与 controller/updater/main 收尾完整集成；父任务架构版本必须明确配套升级、历史迁移及回滚限制。首次可信 writer 启用和线上权限验证仍须按当前任务授权边界执行，不扩大自动合并或部署范围。

## 验收标准

- AC1（R1、R3）：新地址分配与复用完全由 PostgreSQL 应用路径完成；运行中的适配器不再读取或写入永久 identities 表。
- AC2（R2、R7）：旧库迁移前后所有有效历史地址主键、负身份、原坐标和行程/充电外键一致；高于 6 位小数的不同点仍不同；导入重复/冲突/缺失来源有脱敏拒绝结果。
- AC3（R1、R2、R6、R7）：并发首次解析同一精确坐标只持久化一个地址；新序列绕过旧 SQLite 全部分配范围，包括未被 PG 引用的编号。显式 fresh 初始化与旧库导入分别验证，PG 暂无负身份不能自动证明从未分配旧身份。
- AC4（R3、R4）：删除整个适配器缓存、重启服务后，历史地址仍能成功刷新且编号/坐标/关联不变；过期缓存清理不接触永久数据。
- AC5（R5）：供应商/语言切换、境内外与港澳边界、50 项批量刷新及公共 OSM 限流通过回归，模板缓存不会夹带其他请求的身份。
- AC6（R5、R6、R7）：无 Key、上游失败、错误来源、重复或额外返回身份、超时和不匹配协议均明确失败；新适配器路径不合成 Unknown/空白 Address，单地址和迁移提交无半写，lookup 无部分成功列表，应用/适配器日志脱敏。保留上游事件和跨地址/跨批写入边界。
- AC7（R5、R8）：官方默认 Nominatim 路径、URL/Finch pool 校验、旧正身份处理通过对应上游测试；新路径在最终编译 release 中完成真实 PostgreSQL 启动与地址验证。
- AC8（R7、R8）：迁移/恢复和缓存管理文档一致，记录源码测试、隔离镜像测试及未执行的线上动作；不把本地或模拟结果说成云端/生产已验证。
- AC9（R9）：Release 子任务 AC1—AC7 全部按实际证据验收，自动上游更新保持 pin-only，读者能从 Release 确认上游变化、本项目变更、精确双镜像和固定/浮动结果；无法证明的基线不虚构。
- AC10（R8—R10）：架构改动对应可读变更条目说明新所有权、应用/适配器配套版本、显式 fresh/legacy 迁移、不可只降级镜像的回滚边界；正式发布前可信 writer 已启用。缺/失败记录不宣称完整发布；未进行的线上/生产动作明确列为待验证。
